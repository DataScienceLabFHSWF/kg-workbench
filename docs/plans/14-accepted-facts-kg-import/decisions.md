# Entscheidungen

Kurzprotokoll der Architekturentscheidungen für den Import akzeptierter Fakten.

| Datum      | Entscheidung                                                                                             | Begründung                                                                                      | Konsequenz                                                                                                        |
| ---------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 2026-08-31 | Eine Access-Group hat genau einen logischen Knowledge Graph.                                             | Eine lokale Neo4j-Instanz genügt; eine KG-Auswahl ist nicht nötig.                              | Alle KG-Daten werden über den bestehenden `group_key` abgegrenzt.                                                 |
| 2026-08-31 | Der Import läuft serverseitig in Next.js.                                                                | Die Anwendung nutzt bereits TypeScript und Server Actions; Zugangsdaten bleiben auf dem Server. | Neo4j wird über einen serverseitigen TypeScript-Adapter angesprochen; kein Python-Service für V1.                 |
| 2026-08-31 | Dokument-Entitäten werden auf kanonische KG-Knoten abgebildet.                                           | Knoten sollen aus mehreren Dokumenten wiederverwendbar sein.                                    | Die Zuordnung `document_entity_id -> kg_node_id` wird pro Importlauf gespeichert.                                 |
| 2026-08-31 | Entity-Matching ist in V1 nur bei eindeutigem, normalisiertem Namen und gleicher Ontologieklasse sicher. | Verhindert falsche automatische Zuordnungen.                                                    | Mehrdeutige oder abweichende Treffer erhalten den Status `Prüfen`.                                                |
| 2026-08-31 | Der UI-Status trennt Systembewertung und User-Entscheidung.                                              | Ein sicherer Vorschlag ist noch nicht bestätigt.                                                | Sichtbar sind `Sicher`, `Prüfen`, `Geprüft`; die konkrete Entscheidung wird zusätzlich gespeichert.               |
| 2026-08-31 | Änderungen an Fakten oder Entitäten machen einen offenen Importentwurf ungültig.                         | Die Vorschau darf nicht von veralteten Daten importieren.                                       | Jeder Lauf speichert eine Quellenrevision; betroffene Entscheidungen werden neu berechnet.                        |
| 2026-08-31 | Der endgültige Neo4j-Import ist atomar.                                                                  | Teilimporte und ein fälschlich gesperrtes Dokument werden vermieden.                            | Bei Fehlern wird nichts aus dem Lauf geschrieben und das Dokument bleibt bearbeitbar.                             |
| 2026-08-31 | Supabase verwaltet Workflow und Audit, Neo4j den Graph.                                                  | Prozessdaten und kanonische Graphdaten haben unterschiedliche Aufgaben.                         | Supabase speichert Importläufe und Entity-Entscheidungen; Neo4j speichert Knoten, Beziehungen und Provenienz-IDs. |
